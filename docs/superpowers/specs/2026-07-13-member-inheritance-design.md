# 成员传承系统设计

## 目标

为 XP 成员建立只能向更晚期别传递的单线传承关系。在符合资格的成员毕业时，从她毕业当日仍在籍的后辈中一次性抽取继承人；继承人毕业后继续把同一条路线传下去。成员详情只展示直接相邻的上一任和下一任，点击姓名可查看完整传承谱系。

本次工作同时为全部历史毕业成员回填传承关系，并保证今后的毕业操作沿用同一套规则。

## 数据模型

每位成员新增一个 `inheritanceSuccessorId` 字段：

```js
{
  id: "member-id",
  inheritanceSuccessorId: "successor-member-id" // 没有继承人时为 ""
}
```

- 数据库只保存指向下一任的单向边。
- “传承自”通过在成员列表中查找 `inheritanceSuccessorId === member.id` 的成员得到。
- 每位成员最多保存一个下一任，也最多被一个成员指向。
- 无候选人的罕见情况通过可选的 `inheritancePending: true` 标记。公开详情页不展示待定状态，管理员编辑器展示。
- 已经保存的边是历史事实；加载页面、编辑成绩、添加单曲或新增成员时均不得重新抽取。

## 历史时点

### 入团时间

成员的推定入团日为 `selectionHistory` 中第一条非“加入前”记录所对应单曲的发行日。

- 候选继承人的期数必须严格高于毕业成员；同一期成员不能互相继承。
- 候选人推定入团日必须不晚于前任毕业日。
- 候选人在前任毕业日必须仍然在籍：当前在籍，或其毕业日晚于前任毕业日。
- 与前任同日毕业的成员不计为当日在籍候选人，避免在没有具体时间的情况下猜测同日事件顺序。

### 总选时间

按发行时间升序排列 `singleKind === "总选单曲"` 的单曲，第 N 首对应第 N 届总选。某届成绩仅在对应总选单曲发行日不晚于目标日期时计入。

当前数据中六首总选单曲依次对应第一至第六届。第七届暂时没有对应的总选单曲，因此在历史时点资格计算中暂不计入；现有毕业成员均早于第七届，不影响本次回填。

### 选拔时间

选拔次数只统计发行日不晚于目标日期，且 `selectionHistory` 值包含“A面选拔”的单曲。特殊类型单曲只要是 A 面选拔也计入。

## 触发资格

成员在从在籍改为毕业时，若截至毕业日满足以下任一条件，则需要传承：

1. 至少一次总选前三；
2. 至少两次总选前七；
3. 至少三次 A 面选拔。

如果成员已经“传承自”另一位成员，她毕业时无论本人是否满足上述条件，都必须继续当前路线。若她本人后来也达到资格，仍然只延续当前路线，不再开启第二条路线。

## 候选人与抽签优先级

首先筛选同时满足以下条件的候选人：

1. 期数严格更高；
2. 在前任毕业日已经入团且仍在籍；
3. 尚未成为任何人的继承人；
4. 不是前任本人，且加入后不会形成循环。

在有效候选人中建立两个候选池：

1. 优先池：截至前任毕业日尚未取得独立传承资格的成员；
2. 后备池：截至前任毕业日已经取得独立传承资格的成员。

优先池非空时只从优先池随机抽取；仅在优先池为空时从后备池抽取。资格必须按前任毕业当日的历史成绩计算，候选人后来取得的成绩不反向改变抽签结果。

例如坂口阳菜在 2026-03-01 毕业时，前三届总选已经计入。宫岛阿弥已有一次前三，今日优尚未达标，因此今日优属于优先池，宫岛阿弥属于后备池。

## 历史回填

历史回填按毕业日期从早到晚处理，使用固定种子的伪随机顺序，使结果既具有随机性又能稳定复现。

- 需要处理的成员包括：截至本人毕业日已达到资格的成员，以及此前已被选为继承人的毕业成员。
- 若某位达标成员已经是另一条路线的继承人，只延续该路线。
- 回填算法优先遵循未达标候选池，并使用回溯避免早期随机选择导致后续本可完成的成员失去所有候选人。
- 回溯只在满足所有业务约束的选择之间更换结果，不放宽期数、历史在籍或唯一继承规则。
- 如果在全部合法组合下仍无候选人，则写入 `inheritancePending: true`。
- 最终确定的 `inheritanceSuccessorId` 直接写入 `server/data/db.json`，运行时不会再次随机化。

## 未来毕业流程

管理员保存成员编辑时，只有从 `isActive: true` 切换为 `isActive: false` 才检查是否需要抽签。

1. 验证毕业日期和毕业曲等现有必填字段；
2. 判断成员是否已有上一任，或截至毕业日是否达到资格；
3. 如果已经有 `inheritanceSuccessorId`，保持原结果；
4. 否则按历史时点、候选限制和双层优先池抽取一次；
5. 有候选人时保存其 ID，无候选人时标记待定；
6. 后续任何普通编辑都不得触发重抽。

随机数注入到纯函数中，生产环境使用系统随机；测试和历史回填使用固定种子。

## 管理员更正

成员编辑器新增“传承”区域：

- “传承自”只读显示，由数据反向推导；
- “传承至”显示当前下一任，并允许管理员手动更正；
- 待定状态仅在后台显示。

手动更正必须验证：目标存在、期数严格更高、目标在前任毕业日已入团且仍在籍、目标未继承其他人、修改后不形成循环。自动抽签遵循未达标优先级；管理员更正不受优先池限制，但仍必须满足所有硬性约束。

## 详情页交互

在成员详情的 `DETAILS` 与 `ELECTION` 之间增加 `LEGACY / 传承` 区块。

- `传承自`：只显示直接上一任的姓名；
- `传承至`：只显示直接下一任的姓名；
- 某一侧不存在时隐藏该行；两侧都不存在时隐藏整个区块；
- 待定状态不在公开详情显示；
- 点击任一姓名打开“传承谱系”。

传承谱系从没有上一任的根成员开始，沿 `inheritanceSuccessorId` 展示到当前末代成员，并突出当前正在查看的成员。桌面端可横向展示短链，手机端使用纵向排列，避免长姓名和多代链溢出。链解析必须在缺失成员或循环数据时安全停止，不能导致页面崩溃。

## 代码边界

新增独立的传承规则模块，负责：

- 中文及阿拉伯数字总选名次解析；
- 期别、入团日和历史在籍计算；
- 指定日期的资格与资格原因计算；
- 上一任查找、候选池划分和单次抽签；
- 完整链解析与循环保护；
- 手动关系校验；
- 固定种子的历史回填。

`src/App.jsx` 只负责在毕业保存流程中调用规则模块，以及渲染详情、谱系和管理员编辑控件。`server/data/db.json` 保存最终边，不在页面加载时进行迁移或重抽。

## 验证

自动化测试覆盖：

- 第 N 届总选与第 N 首总选单曲日期映射；
- 指定毕业日下的前三一次、前七两次和 A 面选拔三次资格；
- 毕业日之后的成绩不计入；
- 未达标候选优先，优先池为空时才使用已达标候选；
- 候选期数严格更高、当日已加入且仍在籍；
- 同期、同日毕业和已经继承他人的成员被排除；
- 每人最多一个上一任和一个下一任；
- 已加入路线的成员毕业后继续传递且不开新线；
- 抽签结果存在时不重抽；
- 完整链、缺失引用和循环保护；
- 历史回填结果稳定、无重复、无环，并补足全部存在合法候选的应传承成员；
- 详情区块条件渲染和管理员保存流程接线。

最后运行全部 Node 测试、ESLint、Vite 生产构建，并在桌面和 iPhone 尺寸下检查成员详情与传承谱系。
